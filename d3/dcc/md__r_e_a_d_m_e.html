SRDatalog

Column-oriented Datalog engine experiments built with C++23, template metaprogramming (TMP), and a Nim-based query DSL.

Prerequisites

  • xmake 2.8+ in PATH
  • A C++23-capable compiler (clang 17+ or GCC 13+ on macOS/Linux)
  • boost headers (xmake downloads them automatically)
  • Optional: openmpi (only for MPI datatype tests, xmake won't install it automatically, you need to install it manually, mpich setting is in progress)
  • Optional but recommended for the DSL: Nim + nimble

macOS users can install everything via brew install xmake nim.

Environment Bootstrap Script

./setup.sh installs xmake, Nim, and required packages using Homebrew on macOS:

bash setup.sh

Run it once after cloning if you prefer scripted setup; otherwise install dependencies manually as noted above.

Quick Start

# From the project root
xmake f -m releasedbg # configure once (release with debug symbols)
xmake # build everything with the cached config
xmake run test_relation

xmake generates build output under build/<plat>/<arch>/<mode>/. Add -m release for optimized builds.

Continuous Integration

GitHub Actions builds and runs the core tests (test_column, test_semiring, test_relation, test_mpi_type) for every push and pull request. The workflow definition lives at .github/workflows/ci.yml.

Documentation

API documentation is generated with Doxygen through the xmake build docs target. The workflow in .github/workflows/docs.yml builds the HTML and stores it as a downloadable GitHub Actions artifact (docs/build/html). GitHub Pages deployment can be re-enabled later once desired.

Configure Once

Use xmake f (xmake config) to set options that persist for later builds:

xmake f -m releasedbg --build_test_tmp=true # enable TMP + Nim targets
xmake # rebuild with the new config

Target Matrix

  • test_relation – exercises generalized_datalog/relation_col.*
  • test_column, test_semiring – column store and semiring regression tests
  • test_tmp – template-metaprogramming evaluation (needs --build_test_tmp=y)
  • test_nim – Nim DSL integration build (needs --build_test_tmp=y)
  • test_mpi_type – optional MPI datatype check (openmpi must be available)
  • tests – phony default target that depends on all enabled tests

Build or run individual targets:

xmake build test_relation
xmake run test_relation
xmake run test_tmp # only after enabling --build_test_tmp
./srdatalog # run the Nim DSL example

Working with the TMP Playground

  1. Enable the option: xmake f --build_test_tmp=y
  2. Rebuild: xmake build test_tmp
  3. Execute: xmake run test_tmp

The executable prints the TMP evaluation results to stdout. Adjust generalized_datalog/test_tmp.cpp and rebuild.

Nim Query DSL Workflow

The Nim target wraps the C++ runtime and emits C++ ASTs during compilation.

  1. Install Nim & nimble, then enable the TMP option:
    xmake f --build_test_tmp=y
    xmake build test_nim
  2. test_nim triggers nimble build via xmake, producing the srdatalog binary.
  3. After a successful build you will find the executable at the project root:
    ./srdatalog
    The default program (src/srdatalog.nim) declares relations, loads facts, and prints the ZRel output relation.
  4. Edit src/srdatalog.nim to experiment with the DSL. Re-run xmake build test_nim (or simply xmake) to regenerate the binary.

DSL Syntax Primer

The DSL macros live under src/srdatalog/syntax.nim (parsing) and src/srdatalog/codegen.nim (C++ emission). At compile-time they lower Nim syntax to the TMP types in generalized_datalog/. Core forms:

  • srdatalog_prelude() injects the required C++ headers and namespace setup so later emit blocks compile cleanly.
  • datalog_db <BlueprintName>: introduces relation declarations. Use Relation[T1, T2, ...] to create a schema backed by the default BooleanSR semiring, or Semiring[T1, ..., CustomSR] when you need a different semiring as the final type argument.
  • none_recursive_rule <Alias>: describes a non-recursive rule set. Inside the bracket you write {(Head ...) ...} <-- {(Body ...) ...} with an attached pragma block {. name: RuleId order: [x, y, ...] .}. Each head/body tuple is a parenthesised relation call; identifiers become logical variables, while ($"...") embeds raw C++ expressions for constants.
  • edb <DbSymbol>: emits facts. Every tuple is (<Relation> ($"SemiringExpr") ($"col1") ...) which expands to add_fact<Relation>(DbSymbol, ...) in the generated C++.

When expanded, these constructs generate aliases such as AST::RelationSchema, AST::Rule, AST::NonIterativeRuleSets, and the corresponding MIR types, matching what you would otherwise write by hand in C++. Refer to the example below or the implementation files for additional forms (guards ?(...) and := bindings are parsed but still experimental).

Example Usage of the Template Metaprogramming API

#include "ast.h"
#include "query.h"
#include "runtime.h"
#include "semiring.h"
int main() {
using namespace SRDatalog;
using SR = BooleanSR;
using string = std::string;
using RelationR = AST::RelationSchema<AST::TString<'R'>, SR, int, int>;
using RelationS = AST::RelationSchema<AST::TString<'S'>, SR, int, int, int>;
using RelationT = AST::RelationSchema<AST::TString<'T'>, SR, int, int, int>;
using RelationZ = AST::RelationSchema<AST::TString<'Z'>, SR, int, int, int>;
using TriangleDBBlueprint =
AST::Database<RelationR, RelationS, RelationT, RelationZ>;
using x_ = AST::Var<AST::TString<'x'>>;
using y_ = AST::Var<AST::TString<'y'>>;
using z_ = AST::Var<AST::TString<'z'>>;
using h_ = AST::Var<AST::TString<'h'>>;
using f_ = AST::Var<AST::TString<'f'>>;
using rule1 = AST::Rule<
std::tuple<AST::Clause<RelationZ, NEW_VER, x_, y_, z_>>, // Head: Z(x,y,z) with NEW_VER
std::tuple< // Body: R(x,y), S(y,z,h), T(z,x,f) with FULL_VER (default)
AST::Clause<RelationR, FULL_VER, x_, y_>,
AST::Clause<RelationS, FULL_VER, y_, z_, h_>,
AST::Clause<RelationT, FULL_VER, z_, x_, f_>>,
// join plan, the order of variables intersected in the body of the rule
AST::JoinPlan<std::tuple<x_, y_, z_>>>;
using TriangleIDB = std::tuple<AST::NonIterativeRuleSets<rule1>>;
using triangle = AST::Program<TriangleDBBlueprint, TriangleIDB>;
SemiNaiveDatabase<triangle::db_type> db;
// check the compiled indices
using indices = typename AllIndicesFromProgram<triangle, decltype(db)>::type;
using mir_plan = typename CompileRuleToMIR<rule1>::type;
add_fact<RelationR>(db, BooleanSR::one(), 1, 10);
add_fact<RelationR>(db, BooleanSR::one(), 2, 10);
add_fact<RelationR>(db, BooleanSR::one(), 3, 10);
add_fact<RelationR>(db, BooleanSR::one(), 4, 10);
add_fact<RelationR>(db, BooleanSR::one(), 5, 20);
add_fact<RelationR>(db, BooleanSR::one(), 6, 30);
add_fact<RelationR>(db, BooleanSR::one(), 7, 40);
add_fact<RelationR>(db, BooleanSR::one(), 8, 50);
add_fact<RelationS>(db, BooleanSR::one(), 10, 7, 5);
add_fact<RelationS>(db, BooleanSR::one(), 10, 8, 9);
add_fact<RelationS>(db, BooleanSR::one(), 10, 9, 4);
add_fact<RelationS>(db, BooleanSR::one(), 10, 100, 3);
add_fact<RelationS>(db, BooleanSR::one(), 20, 7, 6);
add_fact<RelationS>(db, BooleanSR::one(), 30, 6, 12);
add_fact<RelationS>(db, BooleanSR::one(), 40, 7, 57);
add_fact<RelationS>(db, BooleanSR::one(), 50, 7, 34);
add_fact<RelationT>(db, BooleanSR::one(), 7, 1, 4);
add_fact<RelationT>(db, BooleanSR::one(), 8, 2, 3);
add_fact<RelationT>(db, BooleanSR::one(), 9, 3, 3);
add_fact<RelationT>(db, BooleanSR::one(), 7, 5, 4);
add_fact<RelationT>(db, BooleanSR::one(), 6, 7, 6);
add_fact<RelationT>(db, BooleanSR::one(), 7, 8, 2);
add_fact<RelationT>(db, BooleanSR::one(), 123, 4, 1);
// std::cout << "mir_plan type: " << get_type_name<mir_plan>() << std::endl;
execute_mir_plan<mir_plan, triangle>(db);
print_relation<RelationZ, NEW_VER>(db, std::cout, 10);
return 0;
}
