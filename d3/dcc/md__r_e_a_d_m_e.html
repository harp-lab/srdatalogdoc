SRDatalog

Column-oriented Datalog engine experiments built with C++23, template metaprogramming (TMP), and a Nim-based query DSL.

Prerequisites

  • xmake 2.8+ in PATH
  • A C++23-capable compiler (clang 17+ or GCC 13+ on macOS/Linux)
  • boost headers (xmake downloads them automatically)
  • Optional: openmpi (only for MPI datatype tests, xmake won't install it automatically, you need to install it manually, mpich setting is in progress)
  • Optional but recommended for the DSL: Nim + nimble

macOS users can install everything via brew install xmake nim.

Environment Bootstrap Script

./setup.sh installs xmake, Nim, and required packages using Homebrew on macOS:

bash setup.sh

Run it once after cloning if you prefer scripted setup; otherwise install dependencies manually as noted above.

Quick Start

# From the project root
xmake f -m releasedbg # configure once (release with debug symbols)
xmake # build everything with the cached config
xmake run test_relation

xmake generates build output under build/<plat>/<arch>/<mode>/. Add -m release for optimized builds.

Continuous Integration

GitHub Actions builds and runs the core tests (test_column, test_semiring, test_relation, test_mpi_type) for every push and pull request. The workflow definition lives at .github/workflows/ci.yml.

Nim Query DSL Workflow

The Nim target wraps the C++ runtime and emits C++ ASTs during compilation.

  1. Install Nim & nimble, then enable the TMP option:
    xmake f --build_test_tmp=y
    xmake build test_nim
  2. test_nim triggers nimble build via xmake, producing the srdatalog binary.
  3. After a successful build you will find the executable at the project root:
    ./srdatalog
    The default program (src/srdatalog.nim) declares relations, loads facts, and prints the ZRel output relation.
  4. Edit src/srdatalog.nim to experiment with the DSL. Re-run xmake build test_nim (or simply xmake) to regenerate the binary.

Accessing Generated C++ Files

When Nim compiles your DSL code with the C++ backend, it generates intermediate C++ files that you can inspect to understand how your DSL macros are translated. These files are stored in Nim's cache directory.

Location: The generated C++ files are stored in ~/.cache/nim/srdatalog_d/ (or USERPROFILE%\.cache\nim\srdatalog_d\ on Windows).

File Naming Convention: Nim uses a special naming scheme where module paths are encoded:

  • @mexample@stc.nim.cpp corresponds to src/example/tc.nim
  • @mexample@striangle.nim.cpp corresponds to src/example/triangle.nim
  • @msrdatalog.nim.cpp corresponds to src/srdatalog.nim
  • @msrdatalog@srelation.nim.cpp corresponds to src/srdatalog/relation.nim

The pattern is: @m followed by the module path with @s replacing / separators, then .nim.cpp.

How to Access:

  1. List all generated files:
    ls ~/.cache/nim/srdatalog_d/*.cpp
  2. View a specific generated file:
    # For example, to view the generated C++ for src/example/tc.nim:
    cat ~/.cache/nim/srdatalog_d/@mexample@stc.nim.cpp
    # Or use your preferred editor:
    code ~/.cache/nim/srdatalog_d/@mexample@stc.nim.cpp
  3. Find files by pattern:
    # Find all example files:
    ls ~/.cache/nim/srdatalog_d/@mexample@*.cpp
    # Find all srdatalog module files:
    ls ~/.cache/nim/srdatalog_d/@msrdatalog@*.cpp
  4. View the main entry point:
    cat ~/.cache/nim/srdatalog_d/@msrdatalog.nim.cpp

Note: The cache directory is automatically created when you build the project. If you don't see the files, make sure you've run xmake build test_nim at least once. The files are regenerated each time you rebuild, so they always reflect the current state of your Nim source code.

Alternative: Using nim c --genScript

You can also generate a compilation script that shows exactly how Nim compiles your code:

cd <project_root>
nim c --genScript --backend:cpp src/srdatalog.nim

This will create a shell script (usually compile_*.sh) that shows the compilation commands and intermediate file locations.

DSL Syntax Primer

The DSL macros live under src/srdatalog/syntax.nim (parsing) and src/srdatalog/codegen.nim (C++ emission). At compile-time they lower Nim syntax to the TMP types in generalized_datalog/. Core forms:

  • srdatalog_prelude() injects the required C++ headers and namespace setup so later emit blocks compile cleanly.
  • datalog_db <BlueprintName>: introduces relation declarations. Use Relation[T1, T2, ...] to create a schema backed by the default BooleanSR semiring, or Semiring[T1, ..., CustomSR] when you need a different semiring as the final type argument.
  • none_recursive_rule <Alias>: describes a non-recursive rule set. Inside the bracket you write {(Head ...) ...} <-- {(Body ...) ...} with an attached pragma block {. name: RuleId order: [x, y, ...] .}. Each head/body tuple is a parenthesised relation call; identifiers become logical variables, while ($"...") embeds raw C++ expressions for constants.
  • fixpoint_rule <Alias>: describes a recursive rule set that computes a fixpoint. The syntax is identical to none_recursive_rule, but the head relation may appear in the body. The macro automatically generates rule variants for semi-naive evaluation, using DELTA_VER for incremental relations in the body and FULL_VER for others. This enables efficient iterative computation until convergence.
  • edb <DbSymbol>: emits facts. Every tuple is (<Relation> ($"SemiringExpr") ($"col1") ...) which expands to add_fact<Relation>(DbSymbol, ...) in the generated C++.

When expanded, these constructs generate aliases such as AST::RelationSchema, AST::Rule, AST::NonIterativeRuleSets, AST::Fixpoint, and the corresponding MIR types, matching what you would otherwise write by hand in C++. Refer to the examples below or the implementation files for additional forms (guards ?(...) and := bindings are parsed but still experimental).

Example Usage of the Template Metaprogramming API

#include "ast.h"
#include "query.h"
#include "runtime.h"
#include "semiring.h"
int main() {
using namespace SRDatalog;
using namespace SRDatalog::AST::literals;
using SR = BooleanSR;
using string = std::string;
using RelationR = AST::RelationSchema<decltype("R"_s), SR, int, int>;
using RelationS = AST::RelationSchema<decltype("S"_s), SR, int, int, int>;
using RelationT = AST::RelationSchema<decltype("T"_s), SR, int, int, int>;
using RelationZ = AST::RelationSchema<decltype("Z"_s), SR, int, int, int>;
using TriangleDBBlueprint =
AST::Database<RelationR, RelationS, RelationT, RelationZ>;
using x_ = AST::Var<decltype("x"_s)>;
using y_ = AST::Var<decltype("y"_s)>;
using z_ = AST::Var<decltype("z"_s)>;
using h_ = AST::Var<decltype("h"_s)>;
using f_ = AST::Var<decltype("f"_s)>;
using rule1 = AST::Rule<
std::tuple<AST::Clause<RelationZ, NEW_VER, x_, y_, z_>>, // Head: Z(x,y,z) with NEW_VER
std::tuple< // Body: R(x,y), S(y,z,h), T(z,x,f) with FULL_VER (default)
AST::Clause<RelationR, FULL_VER, x_, y_>,
AST::Clause<RelationS, FULL_VER, y_, z_, h_>,
AST::Clause<RelationT, FULL_VER, z_, x_, f_>>,
// join plan, the order of variables intersected in the body of the rule
AST::JoinPlan<std::tuple<x_, y_, z_>>>;
using TriangleIDB = std::tuple<AST::NonIterativeRuleSets<rule1>>;
using triangle = AST::Program<TriangleDBBlueprint, TriangleIDB>;
SemiNaiveDatabase<triangle::db_type> db;
// check the compiled indices
using indices = typename AllIndicesFromProgram<triangle, decltype(db)>::type;
using mir_plan = typename CompileRuleToMIR<rule1>::type;
add_fact<RelationR>(db, BooleanSR::one(), 1, 10);
add_fact<RelationR>(db, BooleanSR::one(), 2, 10);
add_fact<RelationR>(db, BooleanSR::one(), 3, 10);
add_fact<RelationR>(db, BooleanSR::one(), 4, 10);
add_fact<RelationR>(db, BooleanSR::one(), 5, 20);
add_fact<RelationR>(db, BooleanSR::one(), 6, 30);
add_fact<RelationR>(db, BooleanSR::one(), 7, 40);
add_fact<RelationR>(db, BooleanSR::one(), 8, 50);
add_fact<RelationS>(db, BooleanSR::one(), 10, 7, 5);
add_fact<RelationS>(db, BooleanSR::one(), 10, 8, 9);
add_fact<RelationS>(db, BooleanSR::one(), 10, 9, 4);
add_fact<RelationS>(db, BooleanSR::one(), 10, 100, 3);
add_fact<RelationS>(db, BooleanSR::one(), 20, 7, 6);
add_fact<RelationS>(db, BooleanSR::one(), 30, 6, 12);
add_fact<RelationS>(db, BooleanSR::one(), 40, 7, 57);
add_fact<RelationS>(db, BooleanSR::one(), 50, 7, 34);
add_fact<RelationT>(db, BooleanSR::one(), 7, 1, 4);
add_fact<RelationT>(db, BooleanSR::one(), 8, 2, 3);
add_fact<RelationT>(db, BooleanSR::one(), 9, 3, 3);
add_fact<RelationT>(db, BooleanSR::one(), 7, 5, 4);
add_fact<RelationT>(db, BooleanSR::one(), 6, 7, 6);
add_fact<RelationT>(db, BooleanSR::one(), 7, 8, 2);

Example Usage of the Nim DSL

The project includes two example programs in src/example/:

  1. Triangle Query (triangle.nim): A non-recursive join query that finds triangles in a graph
  2. Transitive Closure (tc.nim): A recursive fixpoint query that computes reachability

Triangle Query Example

This example demonstrates non-recursive rules with multi-way joins:

import srdatalog/lang
srdatalog_prelude()
{.push stackTrace:off.}
proc runDatalog() =
datalog_db TriangleDBBlueprint:
RRel: Relation[int, int]
SRel: Relation[int, int, int]
TRel: Relation[int, int, int]
ZRel: Relation[int, int, int]
none_recursive_rule TriangleNonIter:
[{(ZRel x y z)} <--
{(RRel x y) (SRel y z h) (TRel z x f)}
] {. name: Triangle order: [x, y, z] .}
var arena_full = newArena()
var arena_delta = newArena()
var arena_newt = newArena()
{.emit: """
SemiNaiveDatabase<TriangleDBBlueprint> triangle_runtime(&`arena_full`, &`arena_delta`, &`arena_newt`);
using mir_plan = typename CompileRuleToMIR<Triangle>::type;
""".}
edb triangle_runtime:
(RRel ($"BooleanSR::one()") ($"1") ($"10"))
(RRel ($"BooleanSR::one()") ($"2") ($"10"))
# ... more facts ...
{.emit: """
execute_mir_plan<mir_plan>(triangle_runtime);
print_relation<ZRel, NEW_VER>(triangle_runtime, std::cout, 10);
""" .}
{.pop.}

Transitive Closure Example

This example demonstrates recursive fixpoint rules for computing reachability:

import srdatalog/lang
srdatalog_prelude()
{.push stackTrace: off.}
proc runTC() =
datalog_db TCDBBlueprint:
Edge: Relation[int, int]
Path: Relation[int, int]
# Base case: direct edges are paths
none_recursive_rule TCBaseSet:
[{(Path x y)} <-- {(Edge x y)}] {.name: TCBase, order: [x, y].}
# Recursive case: transitive closure
fixpoint_rule TCFixpointSet:
[{(Path x z)} <-- {(Path x y) (Edge y z)}] {.name: TCTransitive, order: [y, x, z].}
var arena_full = newArena()
var arena_delta = newArena()
var arena_newt = newArena()
{.emit:"""
SemiNaiveDatabase<TCDBBlueprint> tc_runtime(&`arena_full`, &`arena_delta`, &`arena_newt`);
""" .}
edb tc_runtime:
(Edge ($"BooleanSR::one()") ($"1") ($"2"))
(Edge ($"BooleanSR::one()") ($"2") ($"3"))
(Edge ($"BooleanSR::one()") ($"3") ($"4"))
# ... more edges ...
{.emit:"""
execute_query<TCBaseSet>(tc_runtime);
execute_query<TCFixpointSet>(tc_runtime);
auto& path_full = get_relation_by_schema<Path, FULL_VER>(tc_runtime);
std::cout << "path_full size: " << path_full.size() << std::endl;
""" .}
{.pop.}

The transitive closure example shows:

  • Base case rule: Uses none_recursive_rule to initialize paths from direct edges
  • Recursive case rule: Uses fixpoint_rule to iteratively compute transitive paths
  • Semi-naive evaluation: The fixpoint rule automatically generates variants that use DELTA_VER for incremental computation

Both examples can be run via the main srdatalog binary:

./srdatalog
# or
xmake run test_nim
