SRDatalog

SRDatalog (Super Reconfigurable Datalog) is a column-oriented Datalog engine framework built with C++23, template metaprogramming (TMP), and a Nim-based query DSL. The "SR" prefix emphasizes the framework's super reconfigurable architecture, enabling users to build custom Datalog engines by swapping data structure backends, runtime mechanisms, and optimization strategies.

For full documentation, please refer to the docs.

Vision: The ambitious goal of this project is to become **the LLVM for Datalog**—a foundational compiler infrastructure that enables researchers and practitioners to build custom Datalog engines, experiment with new optimization strategies, and target diverse execution environments, all while sharing a common intermediate representation and optimization pipeline.

Architecture

Overview

This repository leverages minimal language features in Nim (only AST macros and {.emit.} blocks), reusing Nim-lang's parser and AST. The system bypasses everything in Nim-lang and directly generates C++ code, while reusing Nim's C++ toolchain to automatically setup compiler and build infrastructure.

The architecture is designed with the ambitious goal of becoming the LLVM for Datalog: a modular compiler infrastructure where frontends (DSL parsers) generate a common intermediate representation (TMP-based AST), which is then optimized and compiled to various backends (different data structures, execution engines, and target architectures). This design enables:

  • Multiple frontends: Different DSLs can target the same TMP-based IR
  • Shared optimizations: Common optimization passes work across all frontends
  • Diverse backends: The same query can target different execution environments (CPU, GPU, distributed, etc.)
  • Research flexibility: Easy experimentation with new optimization techniques and execution strategies

Design Philosophy: Learning from Ascent and Soufflé

SRDatalog draws fundamental inspiration from both Ascent and Soufflé, while addressing their limitations through a multi-level IR architecture and better reconfigurability.

Learning from Ascent: Macro-Based Query Language

SRDatalog fundamentally agrees with Ascent's core ideology: query languages should be macros that expand to the host language (Rust for Ascent, C++ for SRDatalog). This approach provides:

  • Direct integration with the host language ecosystem
  • No separate runtime or interpreter overhead
  • Natural interoperability with existing libraries and code

However, Rust's limitations for HPC libraries became a critical constraint, especially in the context of next-generation supercomputers:

  • CUDA integration: Rust's ownership model (if we have to use unsafe everywhere, we don't use rust) and FFI complexity make it difficult to interface with CUDA libraries, which are fundamentally C/C++-based. This limits GPU acceleration capabilities crucial for heterogeneous supercomputing environments.
  • Next-generation supercomputers: Modern HPC systems like El Capitan, Aurora, and other heterogeneous exascale systems feature complex node architectures with multiple CPU types, GPU accelerators (AMD MI300X, Intel Ponte Vecchio), and specialized processing units. These systems require deep integration with low-level memory hierarchies, NUMA topologies, and accelerator programming models (CUDA, ROCm, oneAPI) that are fundamentally C/C++ ecosystems.
  • Complex node interconnection and hierarchy: Exascale systems have sophisticated network topologies (Slingshot, InfiniBand, custom interconnects) with hierarchical memory systems and specialized communication libraries. Direct C++ integration enables SRDatalog to:
    • Leverage low-level networking primitives and topology-aware placement strategies
    • Optimize for NUMA locality and memory hierarchy (HBM, DDR, persistent memory)
    • Integrate with specialized communication libraries and runtime systems
    • Support advanced features like remote direct memory access (RDMA) and partitioned global address space (PGAS) models
  • MPICH/MPI integration: High-Performance Computing (HPC) libraries like MPICH/OpenMPI are primarily C/C++ based and deeply integrated with system-level features. Rust's memory model and FFI overhead complicate efficient MPI integration, which is crucial for distributed Datalog execution across thousands of nodes in these massive systems.
  • Infrastructure reuse: Many HPC libraries, numerical computing frameworks, and domain-specific optimizations are built on C/C++ ecosystems. By choosing C++ as the host language, SRDatalog can directly reuse this extensive infrastructure without complex FFI layers, enabling seamless integration with the cutting-edge HPC software stack.

Addressing Ascent's Architectural Limitations

While Ascent's macro-based approach is elegant, it suffers from several design limitations that SRDatalog addresses:

1. Monolithic Compilation Model: Ascent's macro compiles directly from AST to Rust code in a single pass. This monolithic design makes it non-reconfigurable:

  • Cannot swap different join algorithms (hash join, sort-merge, worst-case optimal joins)
  • Cannot change storage models (row-oriented, column-oriented, hybrid)
  • Cannot customize ordering strategies and optimization passes
  • Hard to experiment with different execution strategies

2. BYODs (Bring Your Own Data Structures) Complexity: While Ascent's BYODs design is conceptually powerful, it's too difficult to use in practice:

  • Users must implement complex trait hierarchies
  • Heavy boilerplate required for custom data structures
  • Limited guidance on optimal data structure choices
  • Makes experimentation with storage backends cumbersome

3. Non-Declarative Clause Ordering: Ascent's flexible Rust code generation allows arbitrary code nesting, which breaks the declarative nature of Datalog:

  • Clause order matters semantically but appears implicit
  • Makes query optimization harder
  • Reduces clarity about execution semantics
  • Limits compiler's ability to reorder and optimize clauses

SRDatalog's Multi-Level IR Architecture

SRDatalog addresses these limitations through a multi-level IR design with necessary abstraction boundaries:

  1. AST (Abstract Syntax Tree): High-level declarative representation of Datalog rules, relations, and queries. This maintains declarative semantics and enables high-level optimizations.

  2. MIR (Mid-level IR): Compile-time compilation from AST to MIR (CompileRuleToMIR) produces structured operations:

    • ColumnSource: Relation access operations
    • ColumnJoin: Multi-way join operations
    • DestinationRelation: Fact insertion operations

    This intermediate representation enables:

    • Reconfigurable join algorithms: Different MIR interpreters can implement hash joins, sort-merge joins, or worst-case optimal joins
    • Swappable storage models: The same MIR can target row-oriented or column-oriented backends
    • Custom optimization passes: MIR transformations can optimize join order, index selection, and execution strategies
  3. Runtime Execution: The MIR is interpreted at runtime with full type information, enabling efficient code generation while maintaining flexibility.

Benefits of Multi-Level IR Design

  • More Design Flexibility: Different optimization strategies can be applied at different IR levels without affecting others
  • More Optimization Opportunities: AST-to-MIR compilation, MIR transformations, and runtime optimizations can all be customized independently
  • Necessary Limitations: Each IR level enforces declarative semantics and prevents overly flexible code generation that breaks query optimization
  • Reconfigurability: Storage backends, join algorithms, and execution strategies can be swapped at the MIR level without rewriting queries
  • Maintainability: Clear separation between logical (AST), operational (MIR), and execution (runtime) concerns

Provenance and Annotations: A Fundamental Design Principle

SRDatalog treats provenance (annotations) as a fundamental, first-class citizen from the very bottom level of the architecture, not merely as a monomorphism to a single column in relations. This design decision is driven by symbolic AI requirements and enables advanced features like LAT logic (Linear Algebra Temporal logic) and temporal provenance from the ground up.

Provenance as a Core Architecture Component

Unlike systems that treat annotations as an afterthought or simple monomorphism, SRDatalog's annotation system is deeply integrated into the entire IR stack:

  1. AST Level: Semirings are a first-class type parameter in AST::RelationSchema<Name, Semiring, AttrTypesTuple>, making provenance semantics part of the compile-time type system
  2. MIR Level: Annotation propagation and aggregation are explicitly modeled in the Mid-level IR operations, enabling provenance-aware join planning and optimization
  3. Storage Level: While annotations are currently stored as a dedicated column (ann_) in relations, the architecture is designed to support more sophisticated provenance representations beyond simple scalar values

Symbolic AI Requirements: LAT Logic and Temporal Provenance

SRDatalog is designed with symbolic AI requirements as a primary consideration, particularly:

  • LAT Logic (Linear Algebra Temporal Logic): The system is architected to support temporal reasoning and linear algebra operations over annotations. The semiring abstraction provides a natural foundation for representing temporal semantics and linear transformations
  • Temporal Provenance: Time-based provenance tracking is considered from the low-level IR design, allowing annotations to encode temporal information and enabling temporal reasoning at the query level

These requirements are not retrofitted but are fundamental to the IR design, enabling:

  • Annotation-aware optimization: The compiler can optimize queries based on provenance semantics (e.g., idempotent semirings enable different join strategies)
  • Provenance-preserving transformations: IR transformations maintain provenance information throughout the compilation pipeline
  • Custom provenance representations: The architecture allows different annotation models (scalar values, vectors, time-stamped values, etc.) without changing the query structure

Current Implementation and Future Extensibility

Currently, annotations are implemented as a semiring value stored per row (the ann_ column in the runtime Relation<SR, AttrTuple> class). However, the architecture is designed to support more sophisticated representations:

  • Beyond scalar monomorphism: The IR structure can accommodate richer annotation structures (e.g., vectors for multi-dimensional provenance, trees for hierarchical provenance, time-series for temporal provenance)
  • Annotation-aware joins: Join operations can propagate and combine annotations according to semiring semantics, preserving provenance information through complex queries
  • Symbolic AI extensions: The low-level IR design enables future extensions for LAT logic operations, temporal reasoning, and other symbolic AI primitives without architectural changes

This foundational approach to provenance ensures that SRDatalog can serve as a platform for advanced symbolic AI applications that require sophisticated reasoning about data derivation, temporal relationships, and logical annotations.

Meta Language: Nim as a Transitional Choice

Important Note on Meta Language Strategy: The Nim-based DSL in this repository is provided as a transitional solution for planning and to offer users more language choices during the framework's development. However, it's important to acknowledge that the full, final, and complete meta language implementation will be a Racket language module.

Why Nim Currently? Transition Planning and Multiple Options

AST Manipulation and Optimization: Datalog compiler developers can leverage Nim's macro system to easily manipulate the AST of queries. This enables sophisticated optimizations, query rewriting, and even join planning at compile time. The macro system provides a clean, high-level interface for transforming Datalog programs before code generation.

C++ Integration: Nim can be considered as an external macro system for C++. By using Nim's {.emit.} blocks and C++ backend, the framework generates optimized C++ code while providing a more ergonomic metaprogramming environment than raw C++ template metaprogramming. This approach combines the expressiveness of Nim's macros with the performance and ecosystem of C++.

Limitations of the Nim Implementation: The current Nim-based implementation has several limitations:

  • Limited Metaprogramming Expressiveness: While Nim's macros are powerful, they lack the full metaprogramming flexibility and homoiconicity that Lisp-family languages like Racket provide for DSL development
  • Parser Reuse Constraints: The system relies on Nim's parser, which limits syntactic flexibility for domain-specific constructs
  • AST Transformation Overhead: Complex transformations may require more verbose macro code compared to languages designed for language-oriented programming
  • Experimental Status: The Nim DSL is experimental and may not support all planned features of the final metalang

Configurable Backend Architecture: The framework is designed for maximum configurability and reusability. Users can reset the data structure backend by reloading the relations API and executor function, allowing support for different data structures and runtime mechanisms. This makes SRDatalog not just a Datalog engine, but a framework for building your own Datalog engines tailored to specific use cases.

Framework Reusability: The combination of Nim's metaprogramming capabilities and the modular design of the C++ runtime creates a highly reusable framework. Developers can extend the system by:

  • Writing custom AST transformations using Nim macros
  • Implementing new data structure backends by providing alternative relation APIs
  • Creating specialized executors for different runtime environments (e.g., distributed, GPU-accelerated)
  • Customizing optimization passes and query planning strategies

The Final Metalang: Racket: The complete and final meta language implementation will be a Racket language module. Racket's language-oriented programming paradigm, powerful macro system, and homoiconicity make it the ideal choice for building sophisticated DSLs and compiler frameworks. The Racket implementation will provide:

  • Full metaprogramming capabilities for complex AST transformations
  • Native language-oriented programming support for DSL development
  • Flexible syntax extension mechanisms without parser constraints
  • A mature ecosystem for compiler construction and code generation
  • Integration with C JIT compilation libraries for efficient code generation

Transition Strategy: The Nim implementation serves as a practical intermediate step that allows developers to start using the framework while the Racket metalang is under development. This provides users with options during the transition period and helps validate the framework's design.

Template Metaprogramming (TMP) Foundation

The C++ runtime is built on a foundation of template metaprogramming (TMP) that enables compile-time query compilation and optimization. The generalized_datalog/tmp.h module provides essential TMP utilities built on top of Boost.MP11, offering:

TMP Library Dependencies: At the template level, the TMP library heavily relies on C++17 features, Boost.MP11, and Boost.Hana. Any developer working on the TMP layer will need to work directly with these libraries:

  • C++17 features: The TMP code extensively uses C++17 language features such as constexpr if, fold expressions, class template argument deduction, and structured bindings. The overall project requires C++23, but the TMP metaprogramming foundations primarily leverage C++17 features
  • Boost.MP11: Used extensively in tmp.h for type-level tuple operations, type predicates, compile-time type manipulation utilities, and set operations (intersection, difference, uniqueness)
  • Boost.Hana: Used in ast.h for compile-time string literals as template parameters (boost::hana::string) and in runtime.h for heterogeneous containers and compile-time state management (using hana::map for variable bindings)

Developers extending or modifying the TMP layer should be familiar with modern C++ metaprogramming techniques and these library APIs, as the codebase makes extensive use of Boost.MP11 for type-level operations and Boost.Hana for compile-time computation and state management.

  • Type-level tuple operations: Concatenation, intersection, difference, and uniqueness operations on type tuples
  • Type predicates: Compile-time checks for tuple types and type membership
  • Set operations: Efficient type-level set intersection and difference for join planning

These utilities are used throughout the codebase in:

  • ast.h: For defining relation schemas, rules, clauses, and join plans as compile-time types
  • query.h: For compiling AST rules into Mid-level IR (MIR) operations and computing required indexes
  • relation_col.h: For type-safe column-oriented relation operations

TMP-Based Type API: The core of SRDatalog's architecture is its TMP-based type system. Relations, rules, and queries are represented as C++ template types that encode their structure at compile time:

  • AST::RelationSchema<Name, Semiring, AttrTypesTuple>: Represents a relation with its schema (AttrTypesTuple is a std::tuple of attribute types)
  • AST::Rule<HeadTuple, BodyTuple, JoinPlan>: Represents a Datalog rule with its join plan
  • AST::Clause<Relation, Version, Vars...>: Represents a relation call in a rule body or head
  • AST::IfClause<CppExpr>: Represents a conditional filter clause that filters tuples based on a C++ expression
  • AST::LetClause<Var, CppExpr>: Represents a let binding clause that introduces a computed variable
  • AST::CppExpr<CapturedVars, Func>: Represents an inline C++ expression (lambda) used in if/let clauses
  • AST::Var<Name>: Represents a logical variable
  • AST::JoinPlan<VarTuple>: Encodes the join order for efficient execution

Frontend DSL to TMP Code Generation: The Nim-based frontend DSL (src/srdatalog/syntax.nim and src/srdatalog/codegen.nim) generates C++ code that constructs these TMP types. When you write a Datalog query in the DSL:

  1. Parsing: The Nim macros parse the high-level Datalog syntax into an intermediate representation
  2. Code Generation: The codegen module emits C++ code that instantiates the TMP types (e.g., AST::RelationSchema, AST::Rule, AST::NonIterativeRuleSets, AST::Fixpoint)
  3. Compilation: The C++ compiler evaluates these TMP types at compile time, generating optimized join plans and index structures
  4. Execution: The runtime executes the compiled query using the pre-computed join plans and indexes

For example, when you write:

datalog_db TriangleDB:
RRel: Relation[int, int]
SRel: Relation[int, int, int]
none_recursive_rule TriangleRule:
[{(ZRel x y z)} <-- {(RRel x y) (SRel y z)}]

The DSL generates C++ code like:

using RRel = AST::RelationSchema<decltype("RRel"_s), BooleanSR, std::tuple<int, int>>;
using SRel = AST::RelationSchema<decltype("SRel"_s), BooleanSR, std::tuple<int, int, int>>;
using TriangleRule = AST::Rule<
std::tuple<AST::Clause<ZRel, NEW_VER, x_, y_, z_>>,
std::tuple<AST::Clause<RRel, FULL_VER, x_, y_>,
AST::Clause<SRel, FULL_VER, y_, z_>>,
AST::JoinPlan<std::tuple<x_, y_, z_>>
>;

Usage Patterns

Users have two main ways to use this system:

a) Extract compiled Nim -cpp code for inclusion in C++ projects:

  • Compile your Nim code with the -cpp backend
  • Take the generated C++ code and include it in your existing C++ files
  • This allows you to leverage the DSL while maintaining full control over the C++ build process

b) Use Nim as a module system with thin function wrappers:

  • Use Nim as your module system and thin-level function wrapper layer
  • Always put your logic code in emit-cpp blocks within Nim files
  • You can use other Nim libraries (like Nim's C++ std wrapper) to transmit data between Nim and C++ layers
  • This approach provides a clean separation between the DSL/metaprogramming layer (Nim) and the execution layer (C++)

Getting Started

Prerequisites

  • xmake 2.8+ in PATH
  • A C++23-capable compiler (clang 17+ or GCC 13+ on macOS/Linux)
  • boost headers (xmake downloads them automatically)
  • Optional: openmpi (only for MPI datatype tests, xmake won't install it automatically, you need to install it manually, mpich setting is in progress)
  • Optional but recommended for the DSL: Nim + nimble

macOS users can install everything via brew install xmake nim.

bash setup.sh

This installs xmake, Nim, and required packages using Homebrew.

Manual Setup: Install dependencies manually as noted in the Prerequisites section above.

Working with TMP and Nim DSL

TMP Playground:

  1. Enable the option: xmake f --build_test_tmp=y
  2. Rebuild: xmake build test_tmp
  3. Execute: xmake run test_tmp

The executable prints the TMP evaluation results to stdout. Adjust generalized_datalog/test_tmp.cpp and rebuild.

Nim Query DSL:

  1. Install Nim & nimble, then enable the TMP option:
    xmake f --build_test_tmp=y
    xmake build test_nim
  2. test_nim triggers nimble build via xmake, producing the srdatalog binary.
  3. After a successful build you will find the executable at the project root:
    ./srdatalog
    The default program (src/srdatalog.nim) declares relations, loads facts, and prints the ZRel output relation.
  4. Edit src/srdatalog.nim to experiment with the DSL. Re-run xmake build test_nim (or simply xmake) to regenerate the binary.

Accessing Generated C++ Files:

When Nim compiles your DSL code with the C++ backend, it generates intermediate C++ files that you can inspect to understand how your DSL macros are translated. These files are stored in Nim's cache directory.

Location: ~/.cache/nim/srdatalog_d/ (or USERPROFILE%\.cache\nim\srdatalog_d\ on Windows).

File Naming Convention: Nim uses a special naming scheme where module paths are encoded:

  • @mexample@stc.nim.cpp corresponds to src/example/tc.nim
  • @mexample@striangle.nim.cpp corresponds to src/example/triangle.nim
  • @msrdatalog.nim.cpp corresponds to src/srdatalog.nim
  • @msrdatalog@srelation.nim.cpp corresponds to src/srdatalog/relation.nim

The pattern is: @m followed by the module path with @s replacing / separators, then .nim.cpp.

How to Access:

# List all generated files
ls ~/.cache/nim/srdatalog_d/*.cpp
# View a specific generated file
cat ~/.cache/nim/srdatalog_d/@mexample@stc.nim.cpp
# Find files by pattern
ls ~/.cache/nim/srdatalog_d/@mexample@*.cpp
ls ~/.cache/nim/srdatalog_d/@msrdatalog@*.cpp

Note: The cache directory is automatically created when you build the project. If you don't see the files, make sure you've run xmake build test_nim at least once. The files are regenerated each time you rebuild, so they always reflect the current state of your Nim source code.

Alternative: Using nim c --genScript

cd <project_root>
nim c --genScript --backend:cpp src/srdatalog.nim

This will create a shell script (usually compile_*.sh) that shows the compilation commands and intermediate file locations.

Examples

Example Usage of the Template Metaprogramming API

#include "ast.h"
#include "query.h"
#include "runtime.h"
#include "semiring.h"
int main() {
using namespace SRDatalog;
using namespace SRDatalog::AST::Literals;
using SR = BooleanSR;
using string = std::string;
using RelationR = AST::RelationSchema<decltype("R"_s), SR, std::tuple<int, int>>;
using RelationS = AST::RelationSchema<decltype("S"_s), SR, std::tuple<int, int, int>>;
using RelationT = AST::RelationSchema<decltype("T"_s), SR, std::tuple<int, int, int>>;
using RelationZ = AST::RelationSchema<decltype("Z"_s), SR, std::tuple<int, int, int>>;
using TriangleDBBlueprint =
AST::Database<RelationR, RelationS, RelationT, RelationZ>;
using x_ = AST::Var<decltype("x"_s)>;
using y_ = AST::Var<decltype("y"_s)>;
using z_ = AST::Var<decltype("z"_s)>;
using h_ = AST::Var<decltype("h"_s)>;
using f_ = AST::Var<decltype("f"_s)>;
using rule1 = AST::Rule<
std::tuple<AST::Clause<RelationZ, NEW_VER, x_, y_, z_>>, // Head: Z(x,y,z) with NEW_VER
std::tuple< // Body: R(x,y), S(y,z,h), T(z,x,f) with FULL_VER (default)
AST::Clause<RelationR, FULL_VER, x_, y_>,
AST::Clause<RelationS, FULL_VER, y_, z_, h_>,
AST::Clause<RelationT, FULL_VER, z_, x_, f_>>,
// join plan, the order of variables intersected in the body of the rule
AST::JoinPlan<std::tuple<x_, y_, z_>>>;
using TriangleIDB = std::tuple<AST::NonIterativeRuleSets<rule1>>;
using triangle = AST::Program<TriangleDBBlueprint, TriangleIDB>;
SemiNaiveDatabase<triangle::db_type> db;
// check the compiled indices
using indices = typename AllIndicesFromProgram<triangle, decltype(db)>::type;
using mir_plan = typename CompileRuleToMIR<rule1>::type;
add_fact<RelationR>(db, BooleanSR::one(), 1, 10);
add_fact<RelationR>(db, BooleanSR::one(), 2, 10);
// ... more facts ...
execute_mir_plan<mir_plan, triangle>(db);
print_relation<RelationZ, NEW_VER>(db, std::cout, 10);
return 0;
}

#include "ast.h"
#include "query.h"
#include "runtime.h"
#include "semiring.h"
int main() {
using namespace SRDatalog;
using namespace SRDatalog::AST::Literals;
using SR = BooleanSR;
// Define schemas
using RelationR = AST::RelationSchema<decltype("R"_s), SR, std::tuple<int, int>>;
using RelationZ = AST::RelationSchema<decltype("Z"_s), SR, std::tuple<int, int, int>>;
using MyDB = AST::Database<RelationR, RelationZ>;
using x_ = AST::Var<decltype("x"_s)>;

DSL Syntax Primer

The DSL macros live under src/srdatalog/syntax.nim (parsing) and src/srdatalog/codegen.nim (C++ emission). At compile-time they lower Nim syntax to the TMP types in generalized_datalog/. Core forms:

  • srdatalog_prelude() injects the required C++ headers and namespace setup so later emit blocks compile cleanly.
  • schema <SchemaName>: defines a reusable database schema that can be shared across modules and macros. This macro converts the database declarations into a string template that can be passed to other macros. The schema creates a template named <SchemaName>Code() that returns the declarations as a string, enabling code sharing across module boundaries.
  • datalog_db(<BlueprintName>, <SchemaCode>): introduces relation declarations. The first parameter is the database blueprint name, and the second is the schema code (typically from schema macro via <SchemaName>Code()). Use Relation[T1, T2, ...] to create a schema backed by the default BooleanSR semiring, or Semiring[T1, ..., CustomSR] when you need a different semiring as the final type argument.
  • none_recursive_rule <Alias>, <SchemaCode>: describes a non-recursive rule set. The second parameter is the schema code (typically from schema macro). Inside the bracket you write {(Head ...) ...} <-- {(Body ...) ...} with an attached pragma block {. name: RuleId order: [x, y, ...] .}. Each head/body tuple is a parenthesised relation call; identifiers become logical variables, while ($"...") embeds raw C++ expressions for constants.
  • fixpoint_rule <Alias>, <SchemaCode>: describes a recursive rule set that computes a fixpoint. The second parameter is the schema code (typically from schema macro). The syntax is identical to none_recursive_rule, but the head relation may appear in the body. The macro automatically generates rule variants for semi-naive evaluation, using DELTA_VER for incremental relations in the body and FULL_VER for others. This enables efficient iterative computation until convergence.
  • edb <DbSymbol>: emits facts. Every tuple is (<Relation> ($"SemiringExpr") ($"col1") ...) which expands to add_fact<Relation>(DbSymbol, ...) in the generated C++.

If and Let Clauses: Conditional Filtering and Computed Values

SRDatalog supports two advanced clause types for more expressive rules:

  • If Clauses (?(vars...) {.cpp """code""".}): Conditional filtering that allows you to filter tuples based on arbitrary C++ expressions. The expression receives the bound variables as arguments and must return a boolean value. Only tuples where the expression evaluates to true are kept.
  • Let Clauses (var = (vars...) -> Type {.cpp """code""".}): Computed values that introduce new variables bound to the result of a C++ expression. The expression can reference previously bound variables and must return a value of the specified type. The new variable can then be used in subsequent clauses or in the rule head.

If Clause Syntax:

none_recursive_rule MyRule, MyDBCode():
[{(ZRel x y z)} <-- {
(RRel x y),
(SRel y z h),
(TRel z x f),
(?(x) {.cpp """return x % 2 == 0;""".}) # Only keep tuples where x is even
}] {.name: MyRule, order: [x, y, z].}

The if clause (?(x) {.cpp """return x % 2 == 0;""".}) filters tuples where x is even. The C++ code receives the bound variables as function arguments and must return a boolean.

Let Clause Syntax:

none_recursive_rule MyRule, MyDBCode():
[{(ZRel x y sum)} <-- {
(RRel x y),
(sum = (x, y) -> int {.cpp """return x + y;""".}) # Compute sum of x and y
}] {.name: MyRule, order: [x, y, sum].}

The let clause (sum = (x, y) -> int {.cpp """return x + y;""".}) introduces a new variable sum bound to the sum of x and y. The syntax (x, y) -> int specifies the input variables and return type, and the C++ code computes the value.

Combining If and Let:

none_recursive_rule MyRule, MyDBCode():
[{(ZRel x y sum)} <-- {
(RRel x y),
(sum = (x, y) -> int {.cpp """return x + y;""".}),
(?(sum) {.cpp """return sum > 10;""".}) # Only keep tuples where sum > 10
}] {.name: MyRule, order: [x, y, sum].}

Schema Feature: Sharing Code Across Modules and Macros

The schema macro enables sharing database declarations across modules and macros by leveraging Nim's macro expansion order (typed/untyped). Here's how it works:

  1. Schema Definition: Define a schema once using schema MyDB: ... which creates a template MyDBCode() that converts the declarations into a string.
  2. String Conversion: The schema macro uses toStrLit() to convert the database declarations (AST nodes) into a string representation at compile time.
  3. Cross-Module Sharing: With Nim's expansion order (typed macros expand before untyped macros), the schema string can be passed across module boundaries and macro boundaries.
  4. Re-parsing: Inside the implementation macros (datalog_db, none_recursive_rule, fixpoint_rule), the string is re-parsed using parseStmt(decls_str.strVal) to reconstruct the AST for code generation.

This design allows you to:

  • Define a database schema once and reuse it across multiple rules and modules
  • Share schema definitions between different macros that need the same relation declarations
  • Maintain consistency across your Datalog program by having a single source of truth for the database schema

Example:

schema MyDB:
Edge: Relation[int, int]
Path: Relation[int, int]
datalog_db(MyDB, MyDBCode())
none_recursive_rule BaseCase, MyDBCode():
[{(Path x y)} <-- {(Edge x y)}] {.name: Base, order: [x, y].}

When expanded, these constructs generate aliases such as AST::RelationSchema, AST::Rule, AST::NonIterativeRuleSets, AST::Fixpoint, AST::IfClause, AST::LetClause, and the corresponding MIR types, matching what you would otherwise write by hand in C++.
