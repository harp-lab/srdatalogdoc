20  * @section design_overview Design Overview
21  *
22  * SRDatalog is a Datalog engine built with C++ template metaprogramming that
23  * provides compile-time query optimization and efficient runtime execution.
24  * The system follows a multi-stage compilation and execution pipeline:
25  *
26  * @subsection compilation_pipeline Compilation Pipeline
27  *
28  * 1. **AST Definition**: Rules are defined using high-level AST types
29  * (Rule, Clause, Var, etc.) that represent Datalog syntax
30  *
31  * 2. **MIR Compilation**: AST rules are compiled to MIR (Mid-level IR)
32  * operations using CompileRuleToMIR, which generates:
33  * - ColumnSource operations for relation access
34  * - ColumnJoin operations for multi-way joins
35  * - DestinationRelation operations for fact insertion
36  *
37  * 3. **Index Planning**: Required indexes are computed at compile-time
38  * based on join plans and clause access patterns
39  *
40  * @subsection execution_model Execution Model
41  *
42  * The execution uses semi-naive evaluation for recursive rules:
43  *
44  * - **Full Relations**: Complete set of derived facts
45  * - **Delta Relations**: Facts derived in the previous iteration
46  * - **New Relations**: Facts derived in the current iteration
47  *
48  * Each iteration:
49  * 1. Executes rules using delta relations (semi-naive optimization)
50  * 2. Stores new facts in new relations
51  * 3. Merges new into full and swaps new/delta for next iteration
52  * 4. Stops when no new facts are derived (fixpoint reached)
53  *
54  * @subsection join_algorithm Join Algorithm
55  *
56  * The system implements Worst-Case Optimal Joins (WCOJ) using hash
57  * intersection:
58  *
59  * - Each relation column is indexed using HashTrieIndex
60  * - Joins are performed by intersecting hash sets at each level
61  * - This provides optimal worst-case complexity for multi-way joins
62  *
63  * @section memory_management Memory Management
64  *
65  * The system uses polymorphic memory resources (PMR) for efficient memory
66  * allocation:
67  *
68  * - Relations can be allocated on custom memory resources
69  * - This enables arena allocation, memory pooling, and custom allocators
70  * - Indexes share memory resources with their parent relations
71  *
72  * @section performance_considerations Performance Considerations
73  *
74  * - **Compile-time Optimization**: All query planning happens at compile-time
75  * - **Lazy Index Building**: Indexes are built on-demand when accessed
76  * - **Semi-naive Evaluation**: Only processes new facts in each iteration
77  * - **WCOJ Algorithm**: Optimal worst-case join complexity
78  * - **Column-oriented Storage**: Better cache locality for analytical workloads
79  */
