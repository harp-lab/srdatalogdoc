Detailed Description

Runtime execution engine for MIR (Mid-level Intermediate Representation).

This file implements the runtime execution engine that interprets pre-compiled MIR plans. The MIR is a lower-level representation generated from the high-level AST during compilation. The runtime engine:

  • Manages runtime state (variable bindings)
  • Generates iterators from ColumnSource operations
  • Executes multi-way joins using hash intersection (WCOJ)
  • Handles let bindings (C++ expressions)
  • Inserts facts into relations

The execution uses template metaprogramming to generate efficient code at compile time, with runtime execution following the MIR plan structure.

Design Overview

SRDatalog is a Datalog engine built with C++ template metaprogramming that provides compile-time query optimization and efficient runtime execution. The system follows a multi-stage compilation and execution pipeline:

Compilation Pipeline

  1. AST Definition: Rules are defined using high-level AST types (Rule, Clause, Var, etc.) that represent Datalog syntax
  2. MIR Compilation: AST rules are compiled to MIR (Mid-level IR) operations using CompileRuleToMIR, which generates:
    • ColumnSource operations for relation access
    • ColumnJoin operations for multi-way joins
    • DestinationRelation operations for fact insertion
  3. Index Planning: Required indexes are computed at compile-time based on join plans and clause access patterns

Execution Model

The execution uses semi-naive evaluation for recursive rules:

  • Full Relations: Complete set of derived facts
  • Delta Relations: Facts derived in the previous iteration
  • New Relations: Facts derived in the current iteration

Each iteration:

  1. Executes rules using delta relations (semi-naive optimization)
  2. Stores new facts in new relations
  3. Merges new into full and swaps new/delta for next iteration
  4. Stops when no new facts are derived (fixpoint reached)

Join Algorithm

The system implements Worst-Case Optimal Joins (WCOJ) using hash intersection:

  • Each relation column is indexed using HashTrieIndex
  • Joins are performed by intersecting hash sets at each level
  • This provides optimal worst-case complexity for multi-way joins

Transitive Closure Example

The following example demonstrates computing transitive closure using fixpoint evaluation:

using namespace SRDatalog;
using SR = BooleanSR;
// Define relation schemas
using EdgeSchema = AST::RelationSchema<
AST::TString<'E', 'd', 'g', 'e'>, SR, int, int>;
using PathSchema = AST::RelationSchema<
AST::TString<'P', 'a', 't', 'h'>, SR, int, int>;
using TCBlueprint = AST::Database<EdgeSchema, PathSchema>;
// Define variables
using x_ = AST::Var<AST::TString<'x'>>;
using y_ = AST::Var<AST::TString<'y'>>;
using z_ = AST::Var<AST::TString<'z'>>;
// Base rule: Path(x, y) :- Edge(x, y)
using BaseRule = AST::Rule<
std::tuple<AST::Clause<PathSchema, NEW_VER, x_, y_>>, // Head
std::tuple<AST::Clause<EdgeSchema, FULL_VER, x_, y_>>, // Body
AST::JoinPlan<std::tuple<x_, y_>>>;
// Transitive rule: Path(x, z) :- Path(x, y), Edge(y, z)
using TransitiveRule = AST::Rule<
std::tuple<AST::Clause<PathSchema, NEW_VER, x_, z_>>,
std::tuple<AST::Clause<PathSchema, DELTA_VER, x_, y_>, // Use delta
AST::Clause<EdgeSchema, FULL_VER, y_, z_>>,
AST::JoinPlan<std::tuple<x_, y_, z_>>>;
// Create rule sets
using TransitiveBase = AST::NonIterativeRuleSets<BaseRule>;
using TransitiveFixpoint = AST::Fixpoint<TransitiveRule>;
// Initialize database with memory resources
Arena arena_full, arena_delta, arena_newt;
SemiNaiveDatabase<TCBlueprint> db(&arena_full, &arena_delta, &arena_newt);
// Add base facts
add_fact<EdgeSchema>(db, BooleanSR::one(), 1, 2);
add_fact<EdgeSchema>(db, BooleanSR::one(), 2, 3);
add_fact<EdgeSchema>(db, BooleanSR::one(), 3, 4);
// Execute: first copy edges to paths, then compute transitive closure
execute_query<TransitiveBase>(db); // Non-iterative: copies edges
execute_query<TransitiveFixpoint>(db); // Fixpoint: computes closure
// Print results
print_relation<PathSchema, FULL_VER>(db, std::cout, 20);

Example Explanation

  1. Schema Definition: EdgeSchema and PathSchema define binary relations over integers with Boolean semiring annotations
  2. Rule Definition:
    • BaseRule copies edges to paths (non-iterative)
    • TransitiveRule computes transitive paths using DELTA_VER for semi-naive evaluation
  3. Execution:
    • TransitiveBase executes once, copying all edges to Path
    • TransitiveFixpoint iterates until fixpoint:
      • Iteration 1: Finds paths of length 2 (Path(x,y) + Edge(y,z))
      • Iteration 2: Finds paths of length 3, etc.
      • Stops when no new paths are found
  4. Result: Path relation contains all transitive paths reachable from the Edge relation

Memory Management

The system uses polymorphic memory resources (PMR) for efficient memory allocation:

  • Relations can be allocated on custom memory resources
  • This enables arena allocation, memory pooling, and custom allocators
  • Indexes share memory resources with their parent relations

Performance Considerations

  • Compile-time Optimization: All query planning happens at compile-time
  • Lazy Index Building: Indexes are built on-demand when accessed
  • Semi-naive Evaluation: Only processes new facts in each iteration
  • WCOJ Algorithm: Optimal worst-case join complexity
  • Column-oriented Storage: Better cache locality for analytical workloads
