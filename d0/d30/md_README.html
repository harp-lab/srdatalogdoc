SRDatalog

SRDatalog (Super Reconfigurable Datalog) is a column-oriented Datalog engine framework built with C++23, template metaprogramming (TMP), and a Nim-based query DSL. The "SR" prefix emphasizes the framework's super reconfigurable architecture, enabling users to build custom Datalog engines by swapping data structure backends, runtime mechanisms, and optimization strategies.

For full documentation, please refer to the docs.

Vision: The ambitious goal of this project is to become **the LLVM for Datalog**—a foundational compiler infrastructure that enables researchers and practitioners to build custom Datalog engines, experiment with new optimization strategies, and target diverse execution environments, all while sharing a common intermediate representation and optimization pipeline.

Architecture

For detailed architecture and system design documentation, see SYSTEM_DESIGN.md.

For comprehensive documentation on the MIR (Mid-level Intermediate Representation) design, including all instruction types and how they work together, see MIR_DESIGN.md.

Overview: SRDatalog is a column-oriented Datalog engine framework built with C++23, template metaprogramming (TMP), and a Nim-based query DSL. The architecture is designed with the ambitious goal of becoming **the LLVM for Datalog**—a modular compiler infrastructure where frontends (DSL parsers) generate a common intermediate representation (TMP-based AST), which is then optimized and compiled to various backends (different data structures, execution engines, and target architectures).

Key architectural features:

  • Multi-level IR design: AST → MIR → Runtime execution with reconfigurable backends
    • See MIR_DESIGN.md for detailed MIR instruction documentation
  • Provenance as first-class citizen: Semiring-based annotations integrated throughout the IR stack
  • Template metaprogramming foundation: Compile-time query compilation and optimization
  • Nim as transitional meta language: Current DSL implementation (final will be Racket)

Getting Started

Prerequisites

  • xmake 2.8+ in PATH
  • A C++23-capable compiler (clang 17+ or GCC 13+ on macOS/Linux)
  • boost headers (xmake downloads them automatically)
  • Optional: openmpi (only for MPI datatype tests, xmake won't install it automatically, you need to install it manually, mpich setting is in progress)
  • Optional but recommended for the DSL: Nim + nimble
  • Optional: AdaptiveCpp (for SYCL/GPU acceleration support)

macOS users can install everything via brew install xmake nim.

Installing AdaptiveCpp (Optional)

AdaptiveCpp (formerly hipSYCL) provides SYCL support for GPU acceleration. To enable AdaptiveCpp support:

  1. Option A: Automatic build from source (recommended for clang users)
    • When using clang toolchain, xmake will automatically clone and build AdaptiveCpp if not found in the system
    • Requires: clang++, cmake, and ninja to be available
    • Simply enable the flag: xmake f --adaptivecpp=y
    • The build will happen automatically on first use
  2. Option B: Manual installation
    • Follow the official installation guide
    • The recommended approach is to build LLVM with AdaptiveCpp linked in:
      • See: Building an LLVM toolchain with AdaptiveCpp linked in
      • Repository: AdaptiveCpp/AdaptiveCpp
    • Install to a standard location (/usr/local, /usr, or set ACPP_SOURCE_ROOT environment variable)
  3. Enable in xmake: Configure xmake with the adaptivecpp flag:
    xmake f --adaptivecpp=y

The AdaptiveCpp package definition is located in packages/AdaptiveCpp.lua and will:

  • First try to find an existing system installation
  • If not found and clang++/cmake/ninja are available, automatically build from source
  • Otherwise, provide clear error messages about what's needed

Accessing Generated C++ Files:

When Nim compiles your DSL code with the C++ backend, it generates intermediate C++ files that you can inspect to understand how your DSL macros are translated. These files are stored in Nim's cache directory.

Location: ~/.cache/nim/srdatalog_d/ (or USERPROFILE%\.cache\nim\srdatalog_d\ on Windows).

File Naming Convention: Nim uses a special naming scheme where module paths are encoded:

  • @mexample@stc.nim.cpp corresponds to src/example/tc.nim
  • @mexample@striangle.nim.cpp corresponds to src/example/triangle.nim
  • @msrdatalog.nim.cpp corresponds to src/srdatalog.nim
  • @msrdatalog@srelation.nim.cpp corresponds to src/srdatalog/relation.nim

The pattern is: @m followed by the module path with @s replacing / separators, then .nim.cpp.

How to Access:

# List all generated files
ls ~/.cache/nim/srdatalog_d/*.cpp
# View a specific generated file
cat ~/.cache/nim/srdatalog_d/@mexample@stc.nim.cpp
# Find files by pattern
ls ~/.cache/nim/srdatalog_d/@mexample@*.cpp
ls ~/.cache/nim/srdatalog_d/@msrdatalog@*.cpp

Note: The cache directory is automatically created when you build the project. If you don't see the files, make sure you've run xmake build test_nim at least once. The files are regenerated each time you rebuild, so they always reflect the current state of your Nim source code.

Alternative: Using nim c --genScript

cd <project_root>
nim c --genScript --backend:cpp src/srdatalog.nim

This will create a shell script (usually compile_*.sh) that shows the compilation commands and intermediate file locations.

Example Usage of the Template Metaprogramming API

#include "ast.h"
#include "query.h"
#include "runtime.h"
#include "semiring.h"
int main() {
using namespace SRDatalog;
using namespace SRDatalog::AST::Literals;
using SR = BooleanSR;
using string = std::string;
using RelationR = AST::RelationSchema<decltype("R"_s), SR, std::tuple<int, int>>;
using RelationS = AST::RelationSchema<decltype("S"_s), SR, std::tuple<int, int, int>>;
using RelationT = AST::RelationSchema<decltype("T"_s), SR, std::tuple<int, int, int>>;
using RelationZ = AST::RelationSchema<decltype("Z"_s), SR, std::tuple<int, int, int>>;
using TriangleDBBlueprint =
AST::Database<RelationR, RelationS, RelationT, RelationZ>;
using x_ = AST::Var<decltype("x"_s)>;
using y_ = AST::Var<decltype("y"_s)>;
using z_ = AST::Var<decltype("z"_s)>;
using h_ = AST::Var<decltype("h"_s)>;
using f_ = AST::Var<decltype("f"_s)>;
using rule1 = AST::Rule<
std::tuple<AST::Clause<RelationZ, NEW_VER, x_, y_, z_>>, // Head: Z(x,y,z) with NEW_VER
std::tuple< // Body: R(x,y), S(y,z,h), T(z,x,f) with FULL_VER (default)
AST::Clause<RelationR, FULL_VER, x_, y_>,
AST::Clause<RelationS, FULL_VER, y_, z_, h_>,
AST::Clause<RelationT, FULL_VER, z_, x_, f_>>,
// join plan, the order of variables intersected in the body of the rule
AST::JoinPlan<std::tuple<x_, y_, z_>>>;
using TriangleIDB = std::tuple<AST::NonIterativeRuleSets<rule1>>;
using triangle = AST::Program<TriangleDBBlueprint, TriangleIDB>;
SemiNaiveDatabase<triangle::db_type> db;
// check the compiled indices
using indices = typename AllIndicesFromProgram<triangle, decltype(db)>::type;
using mir_plan = typename CompileRuleToMIR<rule1>::type;
add_fact<RelationR>(db, BooleanSR::one(), 1, 10);
add_fact<RelationR>(db, BooleanSR::one(), 2, 10);
// ... more facts ...
execute_mir_plan<mir_plan, triangle>(db);
print_relation<RelationZ, NEW_VER>(db, std::cout, 10);
return 0;
}

Example with If and Let Clauses (C++ API):

#include "ast.h"
#include "query.h"
#include "runtime.h"
#include "semiring.h"
int main() {
using namespace SRDatalog;
using namespace SRDatalog::AST::Literals;
using SR = BooleanSR;
// Define schemas
using RelationR = AST::RelationSchema<decltype("R"_s), SR, std::tuple<int, int>>;
using RelationZ = AST::RelationSchema<decltype("Z"_s), SR, std::tuple<int, int, int>>;
using MyDB = AST::Database<RelationR, RelationZ>;
using x_ = AST::Var<decltype("x"_s)>;
using y_ = AST::Var<decltype("y"_s)>;
using sum_ = AST::Var<decltype("sum"_s)>;
// Rule with let clause: Z(x, y, sum) :- R(x, y), sum = x + y
using LetRule = AST::Rule<
std::tuple<AST::Clause<RelationZ, NEW_VER, x_, y_, sum_>>,
std::tuple<
AST::Clause<RelationR, FULL_VER, x_, y_>,
AST::LetClause<sum_,
AST::CppExpr<std::tuple<x_, y_>,
[](int x, int y) { return x + y; }>>>,
AST::JoinPlan<std::tuple<x_, y_, sum_>>>;
// Rule with if clause: Z(x, y, z) :- R(x, y), S(y, z), x % 2 == 0
using IfRule = AST::Rule<
std::tuple<AST::Clause<RelationZ, NEW_VER, x_, y_, y_>>,
std::tuple<
AST::Clause<RelationR, FULL_VER, x_, y_>,
AST::IfClause<AST::CppExpr<std::tuple<x_>,
[](int x) { return x % 2 == 0; }>>>,
AST::JoinPlan<std::tuple<x_, y_>>>;
SemiNaiveDatabase<MyDB> db;
// ... add facts and execute rules ...
return 0;
}

Transitive Closure Example:

This example demonstrates recursive fixpoint rules for computing reachability with schema usage:

import srdatalog/lang
srdatalog_prelude()
schema TCDBBlueprint:
Edge: Relation[int, int]
Path: Relation[int, int]
{.push stackTrace: off.}
proc runTC() =
datalog_db(TCDBBlueprint, TCDBBlueprintCode())
# Base case: direct edges are paths
none_recursive_rule TCBaseSet, TCDBBlueprintCode():
[{(Path x y)} <-- {(Edge x y)}] {.name: TCBase, order: [x, y].}
# Recursive case: transitive closure
fixpoint_rule TCFixpointSet, TCDBBlueprintCode():
[{(Path x z)} <-- {(Path x y) (Edge y z)}] {.name: TCTransitive, order: [y, x, z].}
var arena_full = newArena()
var arena_delta = newArena()
var arena_newt = newArena()
{.emit:"""
SemiNaiveDatabase<TCDBBlueprint> tc_runtime(&`arena_full`, &`arena_delta`, &`arena_newt`);
""" .}
edb tc_runtime:
(Edge ($"BooleanSR::one()") ($"1") ($"2"))
(Edge ($"BooleanSR::one()") ($"2") ($"3"))
(Edge ($"BooleanSR::one()") ($"3") ($"4"))
# ... more edges ...
{.emit:"""
execute_query<TCBaseSet>(tc_runtime);
execute_query<TCFixpointSet>(tc_runtime);
auto& path_full = get_relation_by_schema<Path, FULL_VER>(tc_runtime);
std::cout << "path_full size: " << path_full.size() << std::endl;
""" .}
{.pop.}

The transitive closure example shows:

  • Base case rule: Uses none_recursive_rule to initialize paths from direct edges
  • Recursive case rule: Uses fixpoint_rule to iteratively compute transitive paths
  • Semi-naive evaluation: The fixpoint rule automatically generates variants that use DELTA_VER for incremental computation

Reference

DSL Syntax Primer

The DSL macros live under src/srdatalog/syntax.nim (parsing) and src/srdatalog/codegen.nim (C++ emission). At compile-time they lower Nim syntax to the TMP types in generalized_datalog/. Core forms:

  • srdatalog_prelude() injects the required C++ headers and namespace setup so later emit blocks compile cleanly.
  • schema <SchemaName>: defines a reusable database schema that can be shared across modules and macros. This macro converts the database declarations into a string template that can be passed to other macros. The schema creates a template named <SchemaName>Code() that returns the declarations as a string, enabling code sharing across module boundaries.
  • datalog_db(<BlueprintName>, <SchemaCode>): introduces relation declarations. The first parameter is the database blueprint name, and the second is the schema code (typically from schema macro via <SchemaName>Code()). Use Relation[T1, T2, ...] to create a schema backed by the default BooleanSR semiring, or Semiring[T1, ..., CustomSR] when you need a different semiring as the final type argument.
  • none_recursive_rule <Alias>, <SchemaCode>: describes a non-recursive rule set. The second parameter is the schema code (typically from schema macro). Inside the bracket you write {(Head ...) ...} <-- {(Body ...) ...} with an attached pragma block {. name: RuleId order: [x, y, ...] .}. Each head/body tuple is a parenthesised relation call; identifiers become logical variables, while ($"...") embeds raw C++ expressions for constants.
  • fixpoint_rule <Alias>, <SchemaCode>: describes a recursive rule set that computes a fixpoint. The second parameter is the schema code (typically from schema macro). The syntax is identical to none_recursive_rule, but the head relation may appear in the body. The macro automatically generates rule variants for semi-naive evaluation, using DELTA_VER for incremental relations in the body and FULL_VER for others. This enables efficient iterative computation until convergence.
  • edb <DbSymbol>: emits facts. Every tuple is (<Relation> ($"SemiringExpr") ($"col1") ...) which expands to add_fact<Relation>(DbSymbol, ...) in the generated C++.

If and Let Clauses: Conditional Filtering and Computed Values

SRDatalog supports two advanced clause types for more expressive rules:

  • If Clauses (?(vars...) {.cpp """code""".}): Conditional filtering that allows you to filter tuples based on arbitrary C++ expressions. The expression receives the bound variables as arguments and must return a boolean value. Only tuples where the expression evaluates to true are kept.
  • Let Clauses (var = (vars...) -> Type {.cpp """code""".}): Computed values that introduce new variables bound to the result of a C++ expression. The expression can reference previously bound variables and must return a value of the specified type. The new variable can then be used in subsequent clauses or in the rule head.

If Clause Syntax:

none_recursive_rule MyRule, MyDBCode():
[{(ZRel x y z)} <-- {
(RRel x y),
(SRel y z h),
(TRel z x f),
(?(x) {.cpp """return x % 2 == 0;""".}) # Only keep tuples where x is even
}] {.name: MyRule, order: [x, y, z].}

The if clause (?(x) {.cpp """return x % 2 == 0;""".}) filters tuples where x is even. The C++ code receives the bound variables as function arguments and must return a boolean.

Let Clause Syntax:

none_recursive_rule MyRule, MyDBCode():
[{(ZRel x y sum)} <-- {
(RRel x y),
(sum = (x, y) -> int {.cpp """return x + y;""".}) # Compute sum of x and y
}] {.name: MyRule, order: [x, y, sum].}

The let clause (sum = (x, y) -> int {.cpp """return x + y;""".}) introduces a new variable sum bound to the sum of x and y. The syntax (x, y) -> int specifies the input variables and return type, and the C++ code computes the value.

Aggregation:

SRDatalog supports aggregation (e.g., count, sum, min, max) within rules. Aggregations are expressed as clauses that bind a result variable to an aggregate function over a relation.

Syntax: (ResultVar = agg_func(Relation arg1 arg2 ...))

Supported functions: count, sum, min, max, exists.

Example:

none_recursive_rule AggRule, MyDBCode():
[{(Counts x c)} <-- {
(Roots x), // Group by x
(c = count(R x y)) // Count y for each x
}] {. name: DoAgg order: [x, c] .}

Combining If and Let:

none_recursive_rule MyRule, MyDBCode():
[{(ZRel x y sum)} <-- {
(RRel x y),
(sum = (x, y) -> int {.cpp """return x + y;""".}),
(?(sum) {.cpp """return sum > 10;""".}) # Only keep tuples where sum > 10
}] {.name: MyRule, order: [x, y, sum].}

Schema Feature: Sharing Code Across Modules and Macros

The schema macro enables sharing database declarations across modules and macros by leveraging Nim's macro expansion order (typed/untyped). Here's how it works:

  1. Schema Definition: Define a schema once using schema MyDB: ... which creates a template MyDBCode() that converts the declarations into a string.
  2. String Conversion: The schema macro uses toStrLit() to convert the database declarations (AST nodes) into a string representation at compile time.
  3. Cross-Module Sharing: With Nim's expansion order (typed macros expand before untyped macros), the schema string can be passed across module boundaries and macro boundaries.
  4. Re-parsing: Inside the implementation macros (datalog_db, none_recursive_rule, fixpoint_rule), the string is re-parsed using parseStmt(decls_str.strVal) to reconstruct the AST for code generation.

This design allows you to:

  • Define a database schema once and reuse it across multiple rules and modules
  • Share schema definitions between different macros that need the same relation declarations
  • Maintain consistency across your Datalog program by having a single source of truth for the database schema

Example:

schema MyDB:
Edge: Relation[int, int]
Path: Relation[int, int]
datalog_db(MyDB, MyDBCode())
none_recursive_rule BaseCase, MyDBCode():
[{(Path x y)} <-- {(Edge x y)}] {.name: Base, order: [x, y].}

When expanded, these constructs generate aliases such as AST::RelationSchema, AST::Rule, AST::NonIterativeRuleSets, AST::Fixpoint, AST::IfClause, AST::LetClause, and the corresponding MIR types, matching what you would otherwise write by hand in C++.
